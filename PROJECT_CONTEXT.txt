WWE OS — ENTERPRISE BUSINESS OPERATIONS PLATFORM
Project knowledge base / context file. Last updated 2026-07-20.

====================================================================
1. WHAT THIS IS
====================================================================
WWE OS is an Enterprise Business Operations Platform: one piece of software
that runs a whole company's operations on a shared platform kernel. It is NOT
an HR app and NOT a developer tool. Its users are business people — owners,
directors, HR managers, accountants, purchase managers, warehouse managers.

HR is simply the first business module planned for migration into the
platform. The platform shell ships first; modules land inside it over time.

Product principle: the user must never feel they switched applications. One
sidebar, one header, one theme, one command palette, one login. Modules
contribute screens, never their own chrome or style.

====================================================================
2. TECH STACK
====================================================================
Frontend (built):
- Next.js 16.2.10 (App Router, Turbopack). NOTE: Next 16 — params is a Promise
  (await params). Read apps/web/node_modules/next/dist/docs/ before app-router
  work; it differs from older Next.
- React 19.2, TypeScript 5, Tailwind CSS v4 (CSS-first, @theme inline).
- shadcn/ui (new-york) + Radix UI, run in monorepo mode.
- TanStack Query, React Hook Form + Zod, next-themes.
- Recharts (chart layer), Lucide icons.
- pnpm workspaces (pnpm 9). Node >= 20.

Backend (planned, not built yet):
- Python / Django + PostgreSQL. Redis for queue/cache.
- Python tooling present: ruff, pytest, pre-commit (pyproject.toml).

Deployment targets:
- Frontend apps -> Vercel
- Backend API + workers/services -> Render
- Database -> managed PostgreSQL
- AI engine -> Cloudflare Tunnel initially, independent later
- Local dev infra via docker-compose: Postgres 5432, Redis 6379, Mailpit 8025

3. REPOSITORY LAYOUT (monorepo)
====================================================================

  web/           The platform shell (Next.js). Everything below lives here.
platform/        Python kernel — cross-cutting capabilities, NO business logic.
                 auth, users, roles, permissions, workflow, notifications,
                 audit, search, storage, tenancy, billing, ai, shared.
                 (README skeletons only; code not written yet.)
modules/         Business modules — ALL business logic goes here (only here).
                 Each has backend/ (api, controllers, services, repositories,
                 models, schemas, serializers, validators, events, tasks,
                 permissions, tests) + frontend, config, docs. Skeletons only.
services/        Independently deployable services (own Dockerfile each):
                 telegram-bot, email-service, webhook-engine, ocr, scheduler,
                 worker, ai-engine. Skeletons only.
packages/        Reusable TypeScript packages (see section 5).
database/        migrations, seed, schemas, backups, docs. Skeleton.
infrastructure/  docker, kubernetes, nginx, github-actions, terraform,
                 monitoring, logging, security, cloudflare, render, vercel.
                 README skeletons.
docs/            architecture, api, deployment, development, roadmap, adr,
                 meeting-notes, design (design bible), modules (blueprints).
scripts/         Dev/ops scripts.
tests/           Cross-cutting e2e/integration suites.

4. ARCHITECTURE RULES (non-negotiable)
====================================================================
1. Business logic ONLY in modules/. platform/ provides capabilities; modules
   provide meaning.
2. Modules never import each other. Cross-module needs go through platform
   contracts or domain events.
3. Never reimplement a platform capability (auth, permissions, workflow,
   notifications, audit, search, storage) inside a module or app.
4. Multi-tenant from day one — tenant-owned data is tenant-scoped
   (platform/tenancy).
5. services/ are deployment-isolated; integrate via API and queue, never via
   source imports.

5. FRONTEND DESIGN SYSTEM (packages/, @bop scope)
====================================================================
@bop/design-system  packages/design-system/src/tokens.css — the ONE source of
                    truth for every color, radius, shadow, and layout metric
                    (OKLCH colors, --layout-sidebar-width 264px,
                    --layout-header-height 56px). Nothing hardcoded elsewhere.
@bop/theme          One ThemeProvider (class-based dark mode, system default).
@bop/ui             Component library: shadcn components + platform primitives
                    (StatusChip, StatusDot, PageHeader, EmptyState).
                    Apps import from @bop/ui/components/* only.
@bop/icons          Lucide, re-exported through one gate. Never import
                    lucide-react directly. No emoji in product UI.
@bop/charts         Themed Recharts layer + chartPalette bound to tokens.
Also: sdk, shared-types, utils, config (placeholder packages for later).

Design identity: calm, engineered ops tool (reference class Linear, Stripe
Dashboard, GitHub Enterprise). Petrol/blue-teal primary. Fonts: Space Grotesk
(display/titles), Inter (body), JetBrains Mono (labels, numbers, kbd). Quiet
elevation; hierarchy from borders/background steps, not heavy shadows.

DESIGN BIBLE: docs/design/design-bible.md is law. Read it before ANY UI
change. If the bible changes, propagate to tokens.css and @bop/ui — the system
changes everywhere or not at all. Covers color, type, spacing, layout,
components, motion, dark mode, accessibility, copy, anti-patterns.

6. THE PLATFORM SHELL (apps/web)
====================================================================
One shell wraps every page (src/components/app-shell.tsx), via the
(platform) route group layout:
- One sidebar (fixed 264px desktop rail + mobile slide-in sheet, same
  component). Groups: Dashboard, Apps, Services (subtle), Administration.
- One header (56px sticky): global search trigger, notification center,
  theme toggle. NO account/user menu — presents as one company system.
- One command palette (Ctrl/Cmd K): search apps + platform pages + theme.
- One notification center (header bell).
- One login page (/login), React Hook Form + Zod validation.
Fully responsive and mobile-first from the start. Light + dark mode.

Company branding lives in ONE file: apps/web/src/config/company.ts
  name = "WWE OS". Edit that file to rebrand everything.

====================================================================
7. EXECUTIVE DASHBOARD (landing page "/")
====================================================================
The landing page is the company COMMAND CENTER, answering one question:
"How is my company doing today?" It is NOT a module launcher and NOT a
software/dev console. It never shows module health, repository status,
deployment status, or development progress.

Sections (ERP-style, like SAP / Oracle / Dynamics / Odoo / ERPNext):
- Time-aware greeting + Quick actions (real navigation: Add employee,
  New purchase, Upload document, New contract).
- Company pulse: 6 KPI tiles — Revenue, Expenses, Pending approvals,
  Employees, Open purchase orders, Low-stock items.
- Financial summary (revenue / expenses / net / cash).
- Procurement, Inventory, People, Contracts summary cards.
- Recent activity feed.
- Pending approvals, Operational alerts, AI insights (attention column).

Business areas live ONLY in the sidebar. The dashboard aggregates across them.

Data contract: apps/web/src/config/dashboard.ts is the single place a backend
fills to make the dashboard live (KPIs, summaries, approvals, alerts,
activity, insights, quick actions). The UI does not change when data arrives.

NO FAKE DATA rule: real numbers where available; genuinely-empty counts read
as 0; unknown monetary figures read "—" with an honest "Awaiting first data"
note. Figures are never invented.

8. BUSINESS MODULES (sidebar apps) + SERVICES
====================================================================
Registry (single source of truth): apps/web/src/config/modules.ts
Sidebar/nav order: apps/web/src/config/navigation.ts

APPS (user-facing, in sidebar):
  HR, Purchases, Inventory, Documents (DMS), Contracts, Assets, Analytics,
  Reports.
  Each opens to a page; real screens replace the placeholder as each backend
  lands. Availability shown in plain words: "In progress" / "Coming soon".

SERVICES (background machinery, shown only on the quiet /services page,
plain-language, nothing to manage):
  Notifications, Approvals, AI Assistant, Document scanning (OCR),
  Email delivery, Telegram alerts.

REMOVED earlier by request (not in the product): Vendor Management, Finance
(as a standalone app), Visitors, Maintenance, Approvals-as-app. (Approvals and
finance summary still appear as dashboard aggregations.)

ADMINISTRATION pages (platform surfaces, not business apps): Users, Roles,
Permissions, Audit, Settings.

Module blueprints (business intelligence, one file each) live in
docs/modules/*.md — purpose, problems solved, users, integrations, database
entities, APIs, dashboard widgets, KPIs, permissions, navigation,
relationships, AI opportunities.

10. COMMANDS
====================================================================
pnpm install                       Install JS deps (repo root).
pnpm --filter web dev              Run web app (http://localhost:3000).
pnpm --filter web build            Production build (must pass before UI done).
pnpm lint / pnpm format            ESLint / Prettier across workspace.
pip install --group dev            Python tooling.
python -m ruff check . / format .  Python lint / format.
docker compose up -d               Local infra (Postgres, Redis, Mailpit).
python -m pre_commit run --all-files   Run git hooks.

Conventions: Conventional Commits (feat(hr): ..., fix(platform/auth): ...).
Architectural decisions -> ADR in docs/adr/.
